Identity, sessions, and delegated access

Follow identity through sign-in, recovery, token issuance, and logout. The security of the whole account depends on each of those paths.

Sign-in and recovery

How it works. Authentication proves who a user is. Recovery can restore access when that proof is lost, so recovery is part of the sign-in system. A user-facing difference in message, status, or timing can disclose whether an account exists. MFA adds assurance only if the server consistently requires it before granting access.

Example. The expense app replies “If an account exists, we’ll send an email” for both known and unknown addresses. A real recovery token is short-lived, single-use, and tied to the intended account and action. The app builds the link from its configured origin.

What to protect. Apply rate limits to both sign-in and recovery. Separate a pending MFA step from a fully authenticated session. Make recovery tokens unusable after consumption or expiry, and decide what a password reset should do to existing sessions. Log outcomes without logging credentials, recovery tokens, or sensitive form fields.

What signs tell you to review recovery separately from sign-in?

Recovery has its own proof, token lifecycle, user-visible responses, and session effects. A strong login flow cannot compensate for recovery that grants access based on weak proof.

Sessions, cookies, and logout

How it works. With a server-side session, the browser usually holds an opaque session identifier in a cookie. The server looks up the session on each request. Secure limits cookie transmission to secure transport, HttpOnly keeps ordinary page scripts from reading it, and SameSite controls when it can accompany certain cross-site requests.

Example. Alice signs in. The app gives her a new session ID so any ID from the pre-login stage cannot become a signed-in credential. On logout, the server invalidates the session and the browser clears the cookie.

What to protect. Use high-entropy IDs, set limits on lifetime and inactivity, rotate IDs at sign-in and privilege changes, and restrict the cookie’s scope. Verify that replaying a previously issued session ID after logout fails in your own regression suite. Treat open WebSockets and cached authorization as separate places that may need revocation.

The __Host- prefix requires Secure, Path=/, and no Domain attribute. A compatible browser keeps this cookie scoped to the host that set it.

Why clear a cookie and revoke the server record?

Clearing ends the browser’s local use of the identifier. Server-side revocation also ends use of any other copy.

OAuth and OpenID Connect

How it works. OAuth gives a client limited permission to call an API. In the authorization code flow, the user approves at the provider, the provider sends a short-lived code back to the client’s registered callback, and the client exchanges the code for an access token. PKCE binds that exchange to the client instance that started it.

Example. You let the expense app read selected receipts from your cloud drive. The drive provider handles your sign-in and asks what access to grant. The app spends an access token at the drive API, within the approved permission. Your drive password stays with the provider. If the expense app also wants to sign you in, OpenID Connect adds an ID token for that client.

What to protect. Request only the needed scopes. Match registered callback URLs exactly. Use authorization code with PKCE, and bind the response to the initiating flow. Protect access and refresh tokens from logs and unintended recipients. When using OIDC, validate the ID token as specified by the protocol. See the dedicated Authentication chapter for more.

Follow the approval from browser to API

  1. The expense app starts a request with only the scope it needs and sends the browser to the drive provider.
  2. After the user approves, the provider sends the browser back to the client’s registered address with a temporary code.
  3. The client checks that the response matches the flow it started and exchanges the code with its PKCE verifier at the token endpoint.
  4. The client uses the resulting access token at the drive API. The API enforces the access granted by the token and its own policy.

Use the app’s own session for subsequent visits to the expense app. Treat access at the drive provider and sign-in to the expense app as separate lifecycles.

What is the difference between an ID token, access token, and refresh token?

The client uses a validated ID token to learn about the authentication event. A resource server accepts an access token intended for its API. A refresh token goes to the authorization server to obtain a new access token under the existing grant.

JWT validation and token lifetime

How it works. JWT is a token format. A common signed JWT carries a header, claims, and a signature or MAC. Signing protects integrity when verified correctly. The claims remain readable unless the token is encrypted separately.

Example. The expense API accepts an access token issued for that API. A validly signed token issued for the reporting API has the wrong audience. Accepting it would grant it meaning it was never given.

What to protect. Use a well-maintained verifier with configured issuers, accepted algorithms, and trusted keys. Check required claims, including intended audience and expiry, and keep validation rules distinct for different token types. Plan key rotation and decide how quickly access must end after an account or permission change. A locally verified token may remain usable until expiry unless the system adds a revocation or policy check.

What does signature verification prove by itself?

It verifies that the token was signed with the expected key and was not changed. The app still checks who issued it, who it was issued for, whether it is current, and what the current operation allows.
