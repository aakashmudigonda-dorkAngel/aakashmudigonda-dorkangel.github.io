Proxies, HTTP framing, and shared caches

When several systems handle the same request, security depends on their decisions agreeing. Review what each one sees and which messages or responses can cross between users.

Web cache deception

How it works. A shared cache keeps responses for multiple users. Deception occurs when it treats an authenticated response as reusable. An edge rule may classify a path as a static asset while the origin routes it to a private page.

Example. The expense app returns one employee’s claim details. The edge policy should prevent that response from entering shared storage, even if the route resembles a cacheable asset.

What to protect. Define cacheable routes explicitly and keep private responses outside shared caching. Use an appropriate response policy such as Cache-Control: no-store where storage is forbidden. Confirm that deployed CDN rules honor the policy and that edge and app routing classify paths consistently.

Verify that the deployed edge respects this response policy for private routes, including routes handled by custom CDN rules.

How would you verify a private route is outside the shared cache?

Run a regression in a controlled environment using two accounts and non-sensitive fixtures. Confirm the personalized responses have the right policy and that the shared cache never serves one user’s response to the other.

Web cache poisoning

How it works. The cache key groups requests it considers equivalent. If the origin varies a response based on an input missing from that key, the cache can serve content from one request to another user.

Example. A public help page varies its language based on a request header. If the cache ignores that header, the first visitor’s language may be shown to everyone. The security concern grows if untrusted input can change redirects, URLs, or active page content.

What to protect. List the inputs that affect each cacheable response. Remove untrusted inputs that should have no effect, or include legitimate variants in the cache policy. Verify the effective key and that supported variations stay separate after the edge processes the request.

What is the simplest way to distinguish poisoning from deception?

In deception, private content should never have been shared. In poisoning, the cache shares content whose value was incorrectly influenced by another request.

Host headers and proxy trust

How it works. HTTP carries the intended hostname. Proxies may also attach information about the original request. The application should trust such metadata only when it comes through the expected proxy boundary and the proxy sets it consistently.

Example. A user asks for a password reset. The app builds the link using its configured public base URL. A request header does not get to choose where the email sends the user.

What to protect. Allow only known hosts at the edge. Have trusted proxies replace incoming forwarding headers before passing them onward. Prevent direct access to the origin where your trust policy assumes a proxy. Review redirects, links, and tenant selection for reliance on trusted host information.

When is it reasonable for an app to trust a forwarding header?

When the request is known to come from an approved proxy that replaces the header using trusted information, and direct access cannot skip that boundary.

HTTP request smuggling

How it works. A persistent HTTP connection can carry several messages. In HTTP/1.1, message framing tells the recipient where each message ends. Smuggling becomes possible when the gateway and backend disagree on those boundaries. Translating between HTTP versions adds another place for interpretation to differ.

Example. An edge forwards requests from many users to an application on a reused backend connection. If the two systems disagree on what belongs to an earlier request, they can stop agreeing on which bytes belong to a later one. That undermines isolation between users.

What to protect. Use maintained components and reject ambiguous message framing before forwarding. Check each hop, including protocol translation, and align behavior across front end and backend. Verify in a controlled integration suite that invalid messages are rejected and unsafe connections are closed.

Framing is separate from routing

Routing decides which service handles a request. Framing decides which bytes make up that request. In HTTP/1.1, a content length counts body bytes and chunked transfer coding describes the body in chunks. A gateway should handle invalid or ambiguous combinations before reusing a connection. Review the gateway-to-origin protocol as well as the browser-to-gateway protocol.

Why start the review at the proxy even if the app code looks correct?

The failure is disagreement between systems before the request reaches normal application logic. The edge and origin must agree about boundaries.
