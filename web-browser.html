Browser security and WebSockets

Separate three browser questions. What can JavaScript read? What will the browser send automatically? What can execute or be clicked in a page?

Same-origin policy and CORS

How it works. The browser treats two URLs as the same origin when their scheme, host, and port match. Same-origin policy generally restricts one origin’s scripts from reading responses from another. CORS is a way for a server to opt into some cross-origin reads. For some requests the browser first checks the server’s policy with a preflight request.

Example. A script on https://expenses.example can read responses from that origin. https://api.expenses.example is cross-origin because the host differs. The API can allow the UI’s origin explicitly. If the UI requests a response with cookies, the API must also allow credentialed access, and the browser’s cookie policies still apply.

Remediation. Use a short allowlist of exact origins for private APIs. If the response’s CORS headers vary with Origin, ensure caches account for Origin. Authenticate API calls and authorize each operation. A browser can send certain cross-origin requests even when it blocks JavaScript from reading the reply.

What the browser checks

  1. The browser identifies the requesting origin. A change from HTTPS to HTTP, to another host, or to a different port changes the origin.
  2. For requests that need preflight, the browser sends an OPTIONS request asking which methods and headers are allowed. If that check fails, the browser stops before making the actual request.
  3. For a permitted cross-origin read, the response includes an Access-Control-Allow-Origin value that matches the requesting origin. A credentialed read also needs Access-Control-Allow-Credentials: true and an explicit origin.

Compare this with CSP. CORS gives a caller’s browser permission to read a response. A CSP directive such as connect-src restricts where the protected page can connect.

These are response headers for the allowed origin. The API still decides whether the caller may see the claim.

What the notes cover

Same-origin reads
Scripts can generally read responses from their own origin. Changing the scheme, host, or port gives you a different origin.
Cross-origin reads with CORS
The private API can grant its known dashboard origin permission to read the response. The API still verifies the user and claim first.

Common pitfall. Treating an origin as just a domain name, or treating the CORS decision as an API permission check.

Why can CORS fail to prevent a private API action?

CORS mostly controls whether browser code gets to read a cross-origin response. Some requests can reach the server without a preflight, and clients outside browsers do not enforce CORS. The API still needs authentication, authorization, and CSRF protection where relevant.

Cross-site request forgery

How it works. CSRF uses the browser’s ability to attach existing credentials, such as a session cookie, when a request is initiated from elsewhere. If the server only checks the cookie, it can mistake the request for the user’s intended action. The response can remain unreadable to the initiating site while the state change still happens.

Example. You’re signed in to the expense app and visit another site. Your browser sends an unexpected request to change your notification email. If the session cookie is included, the server must still verify that the action came through the app’s protected flow.

Remediation. Use the framework’s CSRF protection for cookie-authenticated state changes and keep GET requests free of side effects. A CSRF token is a value the server checks in addition to the cookie. Use a suitable SameSite policy as another layer. Same-site and same-origin are different. For example, sibling HTTPS subdomains can be same-site while having different origins.

Pattern in the notes

Unintended authenticated action
A browser may include the signed-in user’s cookie on a request they did not intend. The server can act on that request even if the other site cannot read the result.

Common pitfall. Protecting only some ways to change an email address, or assuming a response the other site cannot read is harmless. Apply the framework’s CSRF check to every cookie-authenticated action that changes data.

Why might SameSite be insufficient by itself?

Cookie rules depend on the site relationship and navigation, and a same-site origin can still differ from the trusted app origin. Keep server-side CSRF verification for state-changing routes.

Cross-site scripting

How it works. XSS occurs when the browser treats untrusted data as active code in your origin. Reflected XSS returns data in the immediate response. Stored XSS saves it first and may affect other viewers later. DOM-based XSS arises when client-side code sends data to a browser API that interprets it as markup or code. These categories describe both delivery and where the unsafe interpretation happens.

Example. Alice enters a reimbursement memo. Her manager later opens the claim in a privileged view. If the memo is interpreted as active HTML, the manager’s page can act with the manager’s browser privileges.

Remediation. Display plain text through textContent or escaped template interpolation. Use encoding that matches the output context, and validate URL schemes where appropriate. If formatted HTML is required, use a maintained sanitizer. A restrictive Content Security Policy (CSP) adds a separate layer. HttpOnly protects cookie reads by scripts, while scripts running in the app may still make authenticated requests.

Types in the notes

Reflected
The app places request data in the current response. Think of an expense search label displayed on the results page.
Stored
The app saves the value and displays it later. A claim memo can appear in someone else’s review screen.
DOM-based
Browser code handles the value unsafely while building or changing the page. The server response can be unchanged.

Common pitfall. Fixing the submit form while leaving a second renderer, such as the manager’s review page, unsafe. Check every place the data is displayed.

Why is input filtering alone a weak XSS defense?

The same value can be safe in one output context and unsafe in another. Choose a safe rendering API for the destination and test the actual browser view that displays the value.

DOM sources and browser messages

How it works. The DOM represents the current page. A source is where JavaScript gets data, such as the URL, local storage, or a message from another window. A sink is where the script uses it, such as a text node, navigation target, or HTML parser. Review the whole path from source to sink.

Example. A receipt preview frame sends a status message to the expense page. The parent only needs to show “Receipt ready.” Treat the message as structured data, check which origin and window sent it, check the expected message fields, and display the status as text.

Remediation. Set a specific destination origin for sensitive outbound messages. On receipt, verify the sender and validate the data. Choose restricted operations for messages rather than interpreting them as commands or markup.

Pattern in the notes

DOM XSS through web messages
The receipt viewer sends a status to its parent window. The parent should only accept a message from the expected sender and display the status through a text-only API.

Common pitfall. Checking the message format alone. The app needs to verify who sent it and how each accepted field is used.

Can a page have DOM XSS even if its server sends the same static HTML to everyone?

Yes. The client-side script may take a value from the browser and put it into an unsafe sink after the page loads. Review runtime data flow as well as server templates.

Clickjacking and framing

How it works. Clickjacking makes a user interact with a real page while a deceptive interface changes what the user thinks they are clicking. The sensitive button can belong to an authenticated app inside a frame.

Example. A finance approver thinks they are clicking a button on a separate page, but the click lands on the expense app’s approval control. The real page can still carry the approver’s active session if the browser sends the credentials required by that embedded page.

Remediation. Set a restrictive CSP frame-ancestors policy on sensitive pages. Allow framing only where the app deliberately supports it. Check that the policy is delivered as a response header on every relevant route. A state-changing action still needs the usual authorization and CSRF checks.

Pattern in the notes

Misleading a user’s click
The user interacts with a real control while a deceptive page changes what they think they are clicking. A page hosting the real approval button needs a framing policy.

Common pitfall. Relying on a CSRF token to prevent the page from being framed. The real form can already have a valid token.

Would a valid CSRF token stop every clickjacking case?

The click can operate the real form, which may already have a valid token. Framing control addresses where the UI can appear.

WebSockets and live subscriptions

How it works. A WebSocket keeps a connection open for two-way messages. An opening handshake establishes the connection, then both sides can send frames without a separate HTTP request for each message. With wss, the connection is protected by TLS.

Example. Alice subscribes to status updates for her claim. The server authenticates the connection and verifies that Alice can view that claim before subscribing her. After Alice signs out, the service closes the socket or stops serving private updates according to its session policy.

Remediation. For browser clients that use cookies, validate Origin during the handshake against trusted origins. Validate each message’s shape and authorize subscriptions and actions at the resource level. Decide how logout, permission changes, and token expiry affect existing connections. Apply message-size and rate limits.

Where the notes focus

Connection setup
Confirm the browser is allowed to open the socket and identify the user behind it.
Messages after connection
Confirm each requested subscription or action is allowed. The server must also decide how to handle duplicate messages and when latest permissions apply.

Common pitfall. Giving every connected user access to every claim update. A successful handshake identifies the connection, while the subscription check decides which claim it can see.

Why check messages after the connection is authenticated?

Authentication tells us who opened the connection. Each message can request a different action or resource, and the user’s permissions may change while the socket is open.
