Server-side input handling

Find the component that interprets the input. The same value can be harmless as plain text and risky as a SQL expression, shell command, template, path, or URL.

SQL injection

How it works. The database reads SQL as instructions. If the application builds query text by joining it with user input, the database can receive a different instruction than the developer intended. A parameterized query fixes the statement structure and supplies values separately.

Example. A claim search takes a category. The application uses a fixed query with a parameter for the category value. Sorting is a separate choice. The server maps “newest” to a known SQL order instead of inserting arbitrary user input into the query structure.

Remediation. Review raw query construction even when the app uses an ORM. Bind values everywhere, including when previously stored data is later used in a query. Use an allowlist for identifiers or clauses that cannot be bound as values. Give the application the database privileges it needs for its actual job.

The ? placeholders are for values. Select query structure, such as a sort column, from a fixed mapping. The surrounding application still enforces claim access.

SQLi patterns and variants in the notes

Start with the signal. Returned rows are direct. A true or false page change, a conditional error, a timing difference, or an external interaction can reveal behavior without directly displaying query results.

Hidden rows through a changed WHERE clause
The product filter is supposed to return released items in one category. If the database interprets category input as SQL, the visibility condition can stop protecting unreleased rows.
Application logic and authentication
A login lookup can return an account the user has not authenticated as if input changes the query’s logic. Use a bound lookup and verify the password separately with the password-hash verifier.
UNION-based SQL injection
A response that displays query results can also display rows from a combined query. SQL requires compatible result shapes. The notes distinguish column count, compatible types, and multiple values in one displayed field.
Blind SQLi with conditional responses (boolean-based)
The page does not print database rows. A visible difference between two outcomes can still reveal whether a database condition was true or false.
Visible and conditional SQL errors
A verbose error can reveal data directly. In blind error-based SQLi, the useful signal is whether an error happened at all. Use generic public errors and keep sensitive database details in restricted diagnostics.
Blind time-based SQLi
The page and status can look the same while database work takes different amounts of time. Removing visible output does not fix the underlying query.
Blind out-of-band SQLi
An external interaction can reveal that the database performed work even when the page gives no direct signal. Restrict database egress and privileges alongside fixing query construction.
XML encoding and input filters
The notes include a request whose XML representation changes during parsing. Filtering raw text alone is fragile. Bind the decoded value when it reaches the query.

Common pitfall. Assuming an ORM makes every query safe. Check raw queries and any dynamic SQL structure. Test that a normal category search still excludes unpublished or out-of-scope rows.

Why can an ORM-backed app still have SQL injection?

An ORM can expose raw queries or dynamic query fragments. Safety depends on how every value or structural choice reaches the final query.

OS command injection

How it works. A shell turns a command string into executable instructions. If an app mixes user input into that string, the shell may interpret the input as part of the operation. Passing an argument list directly avoids shell parsing, though the selected program may still interpret arguments as options or paths.

Example. The expense app converts an uploaded receipt thumbnail. A library can read image bytes and return a resized image. If the service needs an external converter, it uses a fixed executable, internally generated file names, and approved options.

Remediation. Prefer library functions. Where a subprocess is needed, keep the executable and options fixed, validate input arguments, and run the worker with narrow filesystem and network access. Bound runtime and output size so a conversion error cannot tie up the service.

Types in the notes

In-band
The app returns output from the command, so the result can appear in the response.
Blind
The app does not show command output. The command can still affect the server, including how long the request takes.
Timing and external effects in blind cases
No command output may appear in the response. Extra processing time, an unintended write, or an outbound request can still show that something happened. Restrict equivalent side effects along with removing shell interpretation.

Common pitfall. Hiding command output and calling it fixed. Remove shell interpretation or avoid the subprocess and keep the worker narrowly scoped.

Is it enough to switch from a command string to an argument list?

It removes shell interpretation. The program itself may still treat an argument as an option or as a file to open, so validate inputs against the program’s expected behavior and isolate the process.

Server-side template injection

How it works. A template engine processes a layout with placeholders and may also evaluate expressions. When user text becomes part of the template, the engine can read it as code. The impact depends on the engine and which objects or functions the rendering environment exposes.

Example. The expense app builds an email with a heading and the employee’s memo. Keep the layout in a developer-owned template file and supply the memo as a value. The memo appears as text even if it happens to resemble expression syntax.

Remediation. Avoid interpreting user strings as templates. Keep the rendering context narrow and use the right output encoding when generating HTML. For a feature that genuinely needs user-authored layouts, use a limited format and isolate rendering with constrained privileges.

Behaviors in the notes

Rendered output
A server-side template can evaluate input and show the result when it renders the page or email.
Rendering error
The template engine may reject the input. An error might be the only visible symptom.
Text and expression contexts
The notes distinguish a regular template value from a place where the engine already expects expression syntax. Keep input in value slots and give the renderer only the objects it needs.

Common pitfall. Swallowing template errors while still evaluating submitted strings. Use a fixed layout and pass user text in as a value.

Which boundary distinguishes SSTI from XSS?

SSTI evaluates template syntax on the server. XSS runs active content in the browser. One workflow may require protection at both points.

XML external entity processing

How it works. An XML document can reference entities. With unsafe parser settings, a reference can cause the parser to fetch external content or read a local resource. Even when the response shows no parsed content, an unintended read or network request can still have an effect.

Example. A finance integration imports XML statements. Its parser only needs the submitted fields. The import worker disables external resolution, checks the expected document structure, and does not need broad access to the network or local files.

Remediation. Use secure parser settings that disable external entities and external DTDs. Disable DTD processing entirely where unnecessary. Check third-party document libraries that parse XML internally, and enforce document size and processing limits.

Impacts in the notes

Local resource access
A parser with external resource resolution enabled can read resources accessible to its process.
Outbound requests
Resolving a reference can also make a request from the server, overlapping with SSRF.
Blind resource resolution
The response omits the resolved content, but parser errors or outbound activity can still indicate unexpected resource access.
XInclude and indirect XML processing
File uploads and other formats can reach XML processing through a dependency. Review every XML-related feature in the real parser path and disable features the format does not need.

Common pitfall. Checking the XML document after parsing. Configure the parser to reject external resolution before it reads the untrusted document.

Why might XML schema validation fail to stop XXE?

The parser can resolve references while building the document, before later validation runs. Disable resolution at parser construction and limit the worker’s access.

Insecure deserialization

How it works. Serialization stores data in a format that can be sent or saved. Some deserializers rebuild native objects and call code during construction. Trusting an incoming object graph can therefore give external input control over internal behavior.

Example. A receipt-processing job arrives through a queue. Read a small data record with a claim ID and job type. The worker selects a known handler after checking those fields. A message never chooses a class to load.

Remediation. Use plain data formats with schemas, explicit field selection, and bounded input. Avoid native object deserialization for untrusted input. If legacy internal serialization is unavoidable, constrain who can produce it and restrict the worker’s privileges.

Mechanism in the notes

Rebuilding an object from data
The service turns bytes or text back into an object. A security review asks which object types and behaviors the reader can select while it decodes those bytes.
Object and type changes
A decoder can accept a changed value, type, or object that the application never intended a caller to choose. Model input as a small schema and construct allowed objects explicitly.
Hooks and gadget chains
Native decoding can invoke methods, and those methods can reach other application behavior. Remove untrusted native decoding and isolate legacy readers.

Common pitfall. Believing that object-shaped input is safe once it can be decoded. Accept a small data schema and create only the types the job needs.

Why validate a decoded JSON record if JSON avoids native object construction?

The app may still trust unexpected fields or use values to make dangerous decisions. A schema establishes which fields and types the worker may act on.

JavaScript prototype pollution

How it works. Objects can inherit properties from a prototype. If a merge utility accepts arbitrary keys and changes a shared prototype, unrelated objects may appear to have values they never set. A later permission or configuration check can then use an unintended default.

Example. An expense dashboard merges user preferences into a settings object. Users only need to choose language and theme. The server copies those fields explicitly and keeps permission flags in a separate trusted object.

Remediation. Avoid recursively merging arbitrary user objects into settings. Validate allowed keys at every nesting level, use maps or null-prototype objects for arbitrary-key data where appropriate, and keep merge libraries updated. Use explicitly initialized values for security decisions.

Mechanism in the notes

Shared inherited properties
A change to a shared prototype can affect objects that never set the property directly. In the expense app, a UI preference should only update known preference fields.
Client-side and server-side pollution
In the browser, inherited values can change what a page renders. On the server, they can change application configuration or permission decisions.
URL and JSON inputs
Different structured inputs can reach the same unsafe merge. Copy approved fields into a new object before use.

Common pitfall. Checking just the top-level keys before a recursive merge. Select allowed values explicitly and keep permission flags in trusted objects.

Why can the impact show up in a feature far from the merge?

Other objects can inherit a changed property later. Fix the unsafe write and check that sensitive reads only use trusted, expected data.

Server-side request forgery

How it works. A web feature lets a user influence a request the server makes. The server may have routes to services the browser cannot reach. The risk comes from what the server can connect to and what authority the receiving service gives it.

Example. The expense app imports receipts from an approved storage provider. A constrained fetcher uses the provider’s expected HTTPS destinations. Redirects are disabled or checked against the same policy. Outbound rules prevent the worker from reaching unrelated internal services.

Remediation. Prefer fixed provider endpoints or a strict destination allowlist. When arbitrary public URLs are a real requirement, isolate the fetcher and apply destination policy after resolution and on redirects. Restrict schemes, credentials, response size, and timeouts. Account for cloud metadata and internal address ranges in the network policy.

Types in the notes

Regular or in-band
The app fetches a resource and returns some of the result to the user.
Blind or out-of-band
The app makes a request without returning its result. The destination or an unintended side effect can still matter.
Local service and other backends
A fetcher may reach a service on the same host or elsewhere on a private network. Both destinations need a policy independent of what the browser can reach.

Common pitfall. Trusting the initial URL and overlooking what happens after redirects or name resolution. Enforce the same destination policy throughout the fetch and restrict outbound network access.

Can SSRF matter if the user never sees the response body?

Yes. A request can still perform a state-changing action or reach a private service. Control outbound access irrespective of what the UI returns.

Path traversal and file inclusion

How it works. Path traversal means input can select a path outside the intended storage boundary. File inclusion means the application loads a file as part of processing. Local and remote inclusion describe where that file comes from. The impact depends on whether the app reads content or interprets it.

Example. The receipt download API accepts a receipt ID. It checks claim access and looks up the stored object under that ID. For document templates, a short template name maps to a fixed developer-approved file.

Remediation. Prefer IDs mapped to server-owned records over client-supplied paths. Where paths are necessary, resolve and verify the real destination within the intended directory. Account for symlinks and concurrent filesystem changes in sensitive code. Avoid passing untrusted input to template or module loaders.

Impacts in the notes

Read outside the intended folder
The application opens a file beyond the approved directory. A receipt ID can instead map to a stored file after an ownership check.
Write outside the intended folder
A feature that saves files may overwrite something outside its intended area if it accepts an unsafe path.
Path representation disagreements
A path can change meaning after decoding or resolution. Verify the final path stays inside approved storage and prefer an ID that removes path input entirely.

Common pitfall. Checking only the submitted filename. Prefer a server-generated identifier and verify the actual storage boundary.

Does a correct storage path prove the caller can download the file?

It proves the path is within the permitted storage area. The app still checks whether the caller can access the receipt that path identifies.

File uploads and processing

How it works. A file upload crosses several boundaries. The app accepts bytes, persists them, may decode or transform them, and eventually serves content. Each stage can misinterpret a type, expose private content, or accept more work than it can handle.

Example. The expense app accepts images and PDFs up to a defined size. It generates a storage name, keeps the original private, and processes previews in an isolated worker. The download route checks claim permission before serving it.

Remediation. Validate allowed types and actual content with suitable libraries, and enforce limits on both upload and processing costs. Separate storage from executable locations. Choose safe download headers or a separate origin for untrusted content when appropriate. Review file converters and background workers as their own trust boundaries.

Failure modes in the notes

Misleading file type
A declared content type or extension may disagree with what a decoder sees.
Unsafe placement or overwrite
A file saved at the wrong path can replace an existing file or end up somewhere the server executes files.
Oversized files
Large uploads can exhaust storage or processing capacity.
Different components recognize different file types
An upload can look acceptable to one parser and have a different meaning to another. Use a known decoder for the allowed type, isolate processing, and serve downloads with a deliberate content type.

Common pitfall. Relying on the extension alone. Validate content, put a limit on size and processing, and keep user files outside executable paths.

Why is checking a filename extension insufficient?

The filename is client-supplied, and a worker or browser may interpret the bytes differently. Check content and design the later storage, parsing, and serving steps to contain failures.
