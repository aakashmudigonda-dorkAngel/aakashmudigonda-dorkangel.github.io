API authorization and business logic

Start with actions, objects, and state. A request can be valid HTTP and still ask the app to break one of its business rules.

API inventory and information disclosure

How it works. An API includes more than the routes currently used by the UI. Older versions, bulk exports, documentation, jobs, and admin routes may have different controls. Information disclosure can occur through verbose errors, diagnostics, or bundled deployment artifacts as well as normal responses.

Example. The claim page hides employee bank information, but an old export endpoint returns the full database record. The export is a separate path to the same data and needs its own permissions and field selection.

Remediation. Review route definitions, gateway configuration, and API schemas. Record the accepted methods and inputs, roles, returned fields, and side effects. Use explicit response shapes, safe error messages, and restricted diagnostic access. Review deployed artifacts for secrets and development files.

Examples in the notes

API documentation and route discovery
Documentation can reveal supported routes and inputs. Enforce access and field restrictions at the actual endpoints even when they are absent from the UI.
Information disclosure through diagnostics
Errors and diagnostic responses can reveal internal assumptions. Keep internal metadata out of public responses and apply trust rules at the proxy.
Information disclosure through version history
An old commit or deployed repository artifact may still contain a secret. Keep repository metadata out of deployments and rotate any exposed credential.

Common pitfall. Hiding documentation or deleting a secret from the newest commit and assuming access is fixed. Secure the route, remove the deployed artifact, and revoke exposed credentials.

How would you verify a new API version inherited the old security controls?

Compare routes and response fields and run the same allow-and-deny contract tests on every supported version, including exports and administrative paths.

Object-level access and IDOR

How it works. An insecure direct object reference occurs when a server accepts an object identifier and uses it to look up a resource without verifying the caller’s right to use that resource. Horizontal access distinguishes peers. Vertical access distinguishes roles. A workflow check considers whether the action is allowed in the object’s current state.

Example. Alice and Bob are both employees. Alice may read her own claim but lacks access to Bob’s. A manager can approve a submitted claim for their team, but the same manager may lack permission on another team’s claim or a draft.

Remediation. Scope database queries and permission checks to the authenticated principal and the current tenant. Apply the same policy to individual records, lists, exports, attachments, and batch requests. An unguessable ID can make discovery harder, and the server still needs an access check.

Access-control types in the notes

Horizontal
Two employees have the same role. Alice can read her claim but is denied access to Bob’s.
Vertical
An employee can submit a claim, while only an authorized approver can approve it.
Context-dependent
An approver may approve a submitted claim for their team. A draft or a claim from a different tenant is outside that permission.

Common pitfall. Checking a role once and assuming it gives access to every claim. Check the specific object and workflow state at the server.

What should the regression suite cover?

Check two peer accounts, a higher-privilege role, an unrelated tenant, and a state transition. Confirm that related objects and partial successes in batch operations obey the same policy.

GraphQL and nested permissions

How it works. The GraphQL schema defines types and the fields clients can request. Resolvers fetch or calculate values for those fields. One top-level request can traverse several relationships, and each path to protected data needs to enforce its permissions.

Example. A manager can view a claim and its submitter’s display name. A nested field exposing the submitter’s payroll information requires a different decision. If a resolver assumes permission from the parent object, it may return too much.

Remediation. Enforce object and field access at the resolver or shared business layer. Use request-scoped caching for permission-sensitive results and verify that cache keys include relevant context. Limit depth, breadth, batching, and expensive work using an appropriate cost budget. Schema visibility is a documentation decision and resolver checks protect the data.

Operations in the notes

Queries
Queries read selected fields. Check whether the user may see each protected object or field they request.
Mutations
Mutations ask the system to change data. Check the caller’s role, the target object, and the allowed state change.

Common pitfall. Checking permissions at the top-level route and assuming nested fields or mutations inherit the right policy.

Why does rate limiting by HTTP request count miss some GraphQL load?

A single HTTP request may request many nested fields or bundled operations. Limit the work done by each request as well as the number of requests.

Race conditions and repeated actions

How it works. A race appears when correctness depends on which request finishes first. A typical failure happens when an app reads state, makes a decision, then writes later. Two requests can read the same old value and both decide to proceed.

Example. Two approvals reach the expense app at the same time. Both see a pending claim. If both write and both send a payment event, the claim can pay twice even though its final status looks normal.

Remediation. Enforce the transition in one conditional update or protect it with a transaction and an appropriate lock. Use a uniqueness constraint for rules that must hold across workers. Idempotency keys help the server recognize repeats of the same operation. Separate requests with different keys still need the business invariant. Coordinate downstream events with committed state and test duplicates at the consumer.

Run this after checking the caller’s approval permissions. Continue with the approval event only if the statement changed one row, and coordinate the event with the transaction.

Type in the notes

Limit overrun
Separate requests can each see an unused allowance before either uses it. A one-use gift card, a vote, and a single expense approval share this problem.

Common pitfall. Testing only one request at a time or relying on a disabled button. Enforce the limit where the state changes, then test simultaneous requests and downstream duplicates.

Where would you start if the database shows one approval but finance received two notifications?

Check the boundary between the committed transition and the event delivery. Verify the event is stored with the transition and that retries cannot cause duplicate downstream effects.
