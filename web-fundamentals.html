Request lifecycle

A request to view a claim crosses several systems before the app decides what to return. Knowing who sees what helps you place a security control at the right layer.

DNS and service ownership

How it works. DNS tells a client where a name such as expenses.example is served. A resolver may already have the answer cached. An A or AAAA record maps to an IPv4 or IPv6 address. A CNAME points to another name. The TTL controls how long a cached answer can normally be reused.

Example. The expense app moves to a different edge provider. Some users still reach the old edge while their resolver caches the previous answer. That can make a correct deployment look like an intermittent app failure.

What to protect. Keep an inventory of public names and their owners. Coordinate domain and certificate changes with deployments. Remove obsolete records when a hosted service is retired, and check how long old answers may stay cached.

A rollout works for some users and fails for others. Where would you look first?

Compare DNS answers and timestamps, check which edge each client reaches, and verify that both the old and new endpoints can serve the hostname safely during the transition.

TCP, TLS, and HTTPS

How it works. TCP gives the application a reliable, ordered stream of bytes. With HTTPS over TCP, TLS normally runs before HTTP application traffic. TLS protects data from being read or modified in transit and authenticates the server when the client verifies the certificate chain and hostname. HTTP/3 instead uses QUIC, which integrates TLS and runs over UDP.

Example. Your browser opens expenses.example. If its certificate is for a different name, the browser should stop. Once the TLS connection is established, the browser can send the HTTP request and session cookie over it.

What to protect. Know where HTTPS terminates. If a CDN decrypts traffic, the CDN-to-origin hop is a separate connection with its own trust configuration. Inventory certificates, validate names at each client-facing hop, and monitor renewal failures. TLS authenticates a connection, while the app authenticates users and authorizes access to claims.

DNS finds the destination before a fresh connection when a lookup is needed. It sits outside the HTTP message. For HTTP/3, QUIC over UDP takes the place of TCP and integrates TLS.

Does HTTPS mean a claim is safe from unauthorized users?

HTTPS protects traffic between endpoints. The API still needs to verify the session and check permission on the specific claim, and internal hops need their own protection.

Follow one HTTP request

How it works. An HTTP request has a method, a target, headers, and sometimes a body. A reverse proxy or gateway may route it, terminate TLS, and add trusted connection metadata. A cache may answer the request or forward it. The app authenticates the session, checks the operation, and asks storage for the result.

Example. When Alice opens a claim, the browser sends the claim ID. The API loads the claim within Alice’s tenant and checks that she can read it. The response can carry a policy preventing shared caching. Logs can record a request ID and the decision without retaining the session token or claim contents.

What to protect. Trace one request across browser, gateway, app, and storage. Write down where identity first becomes trusted, where the resource is selected, and where the response could be reused. Confirm that monitoring can distinguish a routing problem, a session failure, and an authorization denial.

How do you begin a white-box review of a web feature?

Draw the request path, name the sensitive data and side effects, find the actual enforcement points in code and configuration, and write a regression check for each boundary.
